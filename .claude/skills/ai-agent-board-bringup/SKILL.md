# ai_agent 上板排障

`packages/ai_agent` 是「能听会说」的那一层，但它默认配置基本跑不起来，而且失败方式
很安静——没有报错，只是没声音、没回复、没提醒。下面每一条都对应一个真实的长时间误判。

## 配置：默认几乎全是关的

最小可用集合（板级 defconfig）：

```
CONFIG_EXAMPLES_AI_AGENT_VELA=y
CONFIG_EXAMPLES_AI_AGENT_VELA_STACKSIZE=65536
CONFIG_AI_AGENT_AUDIO_ALSA_DIRECT=y
CONFIG_AI_AGENT_AUDIO_CAPTURE_GAIN=1
```

要 MQTT 再加 **两个都得开**：

```
CONFIG_AI_AGENT_MQTT=y
CONFIG_NETUTILS_MQTTC=y        # ← 只开上面那个不够
```

**改完要删掉相关 `.o` 强制重编。** 这套构建不跟踪头文件依赖，配置开关变了但已编译的
对象还在，会链接出一个「开关开了但代码是旧的」的二进制——表现是新功能完全不生效，
而且没有任何提示。详见 `openvela-build-traps`。

## 超时：`thinking` 默认开着，会顶穿 60 秒

MiMo v2.5 的 thinking 默认**开**，一次推理 90–100 秒，超过客户端 60 秒超时 → 用户看到
的是「Sorry」。要显式关掉：

```
thinking: {type: "disabled"}
```

**先量延迟再调超时**，不要反过来——90 秒不是网络慢，是模型在思考。

## TLS：端点是个负载均衡，个别 IP 的握手窗口是坏的

**症状**：TTS 时有时无。同一句话，有时正常，有时完全没声音；重试一次又好了。

**误判**：一开始怀疑是证书算法（Ed25519）不被 mbedTLS 支持。实际去查那个 IP，RSA
证书是健康的——所以不是算法问题。

**真因**：端点后面是 ALB，**个别后端 IP 在某段时间里握手必失败**。DNS 轮询到它，
请求就哑了。

**修法**（按代价从小到大，我们都是这么叠上去的）：

1. **逐个 IP 回退**：解析出全部 A 记录，一个失败换下一个，别绑死第一个
2. **指数退避**：连续失败时退避，别原地重试把坏窗口撞得更狠
3. **重试次数够多、退避封顶**：我们最后是 8 次、封顶 4 秒
4. **握手成功但响应 MAC 校验失败也要整请求重试**——这类失败看起来像「服务端返回了
   坏数据」，其实同样是那个坏窗口的另一种表现

日志里能看到 TLS 握手失败的 IP，把 IP 打进日志，否则你分不清是同一个 IP 一直坏还是
在轮询。

## chunked keep-alive：每句话卡二十秒

**症状**：TTS 每句开头卡 ~20 秒，然后正常。

**真因**：`tls_read_response` 对 **keep-alive 的 chunked 响应**会一直读到服务端主动
关闭连接。而 keep-alive 的目的就是不关。于是每句都要等一次空闲超时。

**修法**：解析 chunked 编码，读到终止块（`0\r\n\r\n`）就停，不要等 EOF。写个
`chunked_body_complete()` 判断。

**判断依据**：卡顿时间是**固定**的（等于某个超时值），不是随长度增长——这说明在等
超时，不是慢。

## 回复缓存：有状态请求会被缓存成错的答案

**症状**：问同一个问题，收到的是**上一次**的答案。

**真因**：response cache 的 key 用了「当前消息」，而这个消息在进缓存前被截断到 64 字节。
多轮对话里前缀相同，key 就撞了。

**修法**：对**有状态**的客户端（带会话历史、带 `chat_id` 的）直接关掉响应缓存。
缓存只对无状态的单轮问答有意义。

## MQTT 两个坑

### 双 sync 线程用同一个 client_id 互踢

**症状**：`mqtt_sync` 一直返回 `-2147483631`，循环往复。

**真因**：有两条路径都会启动 sync 线程，它们用**同一个 client_id** 连 broker，
broker 把对方踢下线，两条线程互相踢。

**修法**：`start` 做成幂等（已在跑就直接返回），`stop` 要**等线程真的退出**再返回，
不能只发个信号就走。

### 单线程 dispatch 被一个慢连接卡死

**症状**：**提醒到点不响**，但手动说话一切正常。

**真因**：outbound dispatch 是单线程，一个卡住的 MQTT 连接会**阻塞整条队列**——
后面所有消息都出不去。表现是「提醒功能坏了」，实际是 MQTT 把队列堵了。

**修法**（三处都要）：

- `connect` 加超时 + 只初始化一次
- `recv` 里释放锁，别攥着
- `sendall` 遇到 `EAGAIN` **直接返回**——原来的实现是 `usleep` 原地死循环重试，
  还持着锁，直接把 dispatch 线程焊死

**教训**：一个「提醒不响」的 bug，根因可能在完全不相干的 MQTT 层。排障时先看
**整条链路有没有被别人堵住**，再怀疑提醒模块自己。

## CLI 与后台守护进程是同一个实例

板子启动时拉起的 daemon，和你在串口敲配置命令起的 CLI，**共用同一个实例**。
所以 `quit` 不能把 daemon 也一起杀掉——否则你退一次 CLI，语音功能就没了。

判断这类问题的方法：**看进程还在不在**。功能「消失」但进程活着 → 状态问题；
进程没了 → 生命周期问题。

## 排障顺序

1. 进程还活着吗？→ 不在就是崩了/没启动，先看 rcS 和启动日志
2. 配置开关真的生效了吗？→ 删 `.o` 重编，别信「我改了 defconfig」
3. 有声音吗？→ 没有就查 TLS 多重试与 codec（见 `voice-loop-tuning`）
4. 有声音但内容是旧的？→ 查响应缓存
5. 只有某条链路不工作（提醒/上报）？→ 查共享的 dispatch 队列有没有被堵
