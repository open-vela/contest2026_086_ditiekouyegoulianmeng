## 二、WiFi 多网络（v2.81 已改成 C 实现）

> ⚠️ v2.80 及以前，开机连 WiFi 走 `/etc/wifi/start_wifi.sh`。这块板子的 `sh`
> 是 NSH：**没有位置参数、没有 `VAR=value`、没有 `grep`、不支持循环**，
> 脚本在真板上只会刷一串 `command not found`，然后拿着空 SSID 去连（拿到
> 10.0.0.2 这种假地址）。v2.81 把候选逻辑搬进了 C
> （`network_wifi_boot_connect()`），脚本只剩一句提示。

现在的开机顺序：`set_wifi` 保存的凭据 → `/data/etc/wifi/networks.d/0{1,2,3}.conf`
→ `/data/etc/wifi/wapi.conf` 兜底。第一个拿到 IP 的就赢，并写成新的默认。

| # | 做什么 | 该看到什么 | 结果 |
| --- | --- | --- | --- |
| 2.1 | 烧完第一次开机，看串口 | 没有 `command not found` 刷屏，也没有 `Found iface wlan0 addr` 每秒一行 | |
| 2.2 | `ai_agent` → `set_wifi <SSID> <密码>` | `[netmgr] WiFi connected: 192.168.x.x` | |
| 2.3 | **不重启**，等几秒 | 出现 `Network came up late` 和 `All network services started!` —— MQTT 自己起来 | |
| 2.4 | **重启板子** | 先试保存的凭据，日志 `WiFi connected`；字幕板最后显示「可以开始」 | |
| 2.5 | 加一个备选：`echo '{"ssid":"手机热点","psk":"密码"}' > /data/etc/wifi/networks.d/02.conf` | 重启后第一张网连不上时会试它，日志 `Boot WiFi: trying 手机热点` | |
| 2.6 | **两个网络都关掉**再重启 | 日志 `Boot WiFi: no candidate connected` + `Network timeout`，板子不卡死，脸还能看 | |
| 2.7 | **现场演练**：只开手机热点，重启 | 板子自己连上热点，最后显示「可以开始」 | |

**2.1 和 2.3 是这次的核心**：前者证明刷屏没了，后者证明运行中 `set_wifi`
之后服务会自己起来，不用靠重启。

> `networks.d` 目录由 ai_agent 开机时自己 `mkdir`（NSH 没有 mkdir 命令）。
> 如果 2.5 的 `echo` 报 `No such file or directory`，说明那条路径没建起来，
> 回来告诉我，别硬试。

## 七、孩子的冒险记录（第 14 条改动）

> 这条改动横跨板子和家长端，而且是**新协议**（切片回传），所以要独立验一节。
> 协议往返在 Linux 上用真实中文历史跑过 7 项检查，家长端渲染也截图确认过。
>
> **2026-10-27 上板实测栽过**：手机停在「收到 3/6 片」，故事书空白。串口是
> `history chunk 2/6 publish failed: err=-2147483632`（2/4/6 片全丢）。
> 根因是 1 KB 发送缓冲放不下两条 QoS1 消息，且失败那片已经推进了 offset。
> v2.82 已修（缓冲 2048、每片 256 字节、失败重发），这一节按 v2.82 重新验。

| # | 做什么 | 该看到什么 | 结果 |
| --- | --- | --- | --- |
| 7.1 | 在板子上说「我们来玩冒险游戏」，讲 3~4 轮，然后退出故事模式 | 正常（这一段本来就是主链路） | |
| 7.2 | 看串口有没有 `history:` 开头的行 | 点同步之前**不应该有** | |
| 7.3 | 手机端点「同步」 | 卡片标题栏依次显示「同步中…」→「收到 N/M 片」→「本机共 N 条」 | |
| 7.4 | 看卡片里的内容 | 出现刚才那几轮对话 —— **孩子的话带蓝色「孩子：」，故事正文缩进灰字** | |
| 7.5 | **重点看中文有没有乱码** | 一个字都不该乱 | |
| 7.6 | 看串口日志 | `history: kid_buddy:story -> parent, NNNN 字节, M 片，开始发送` 然后 `发送完成，共 M 片`；**整段不该出现 `发不出去` / `publish failed` / `Reconnecting`** | |
| 7.7 | **再点一次「同步」** | 条数**不翻倍**（去重生效），仍是「本机共 N 条」 | |
| 7.8 | 再讲**第二段**冒险（可以隔几分钟），再同步 | 显示成**两张卡片**，各自带时间头，不混在一起 | |
| 7.9 | 断开 broker，再点「同步」 | 提示「未连接，先连上 broker 再同步」，不崩 | |
| 7.10 | 关掉页面重开 | 冒险记录**还在**（存在手机本地，不依赖板子在不在） | |

**7.5 是最可能出问题的一条。** 中文乱码的话，八成是分片拼接那一环
（每片 base64 不能直接拼接后整体解码，见 `phone-app/README.md` 里的警告），
把「正常字符 + 乱码字符」一起截图发我。

**7.3 如果卡在「收到 N/M 片」不动了**，说明有切片没到 —— 把串口日志
（`history chunk X/Y 发不出去` 那几行）发我。v2.82 起单片失败会自动重发，
所以正常情况下不该再看到这行；如果看到，说明是网络真的断了，不是缓冲问题。

**已知边界**：

- PG13 原来是蓝牙 PCM 位时钟，用掉之后蓝牙音频不能用（固件本来也没用）。
  H4 上如果插了 3-4 的跳线帽，先拔掉。**第 3 脚 = PG13（BT_PCM_CLK）**；
  第 1 脚是 PG14（BT_PCM_DOUT）、第 7 脚是 PG12（BT_PCM_SYNC），接错不会有波形。
  2026-11-04 真机结论：**PWM2 在 PG13 上是 mux 5，不是按功能表数出来的 6。**
  用 v2.90 的慢扫确认：拉高 8 秒时 H4 第 3 脚两次都是 3.3V（脚位对），
  mux=5 那一档闪了 5 下（复用号对）。v2.91 已把它写成默认值并删掉自检代码；v2.92 再修了起呼相位。
- 常亮亮度写死在 `led_strip.c` 的 `STRIP_STEADY_PCT`（40%），呼吸最高亮度
  `STRIP_MAX_PCT`（60%），周期 `STRIP_BREATH_MS`（4000 ms）。要改就改这三个，
  别去动 PWM 寄存器。
- 「思考」的判定条件是 `g_reply_busy && g_llm_turn && !g_obs_speaking`，
  在 `face_apply()` 里每 100 ms 同步一次；「回传故事书」由
  `mqtt_channel.c` 的 `s_hist_buf` 生命周期驱动。两边都只置/清位，互不覆盖。

## 十八、v2.93 两处修复（未上板验证）

### 18A. 故事书里要能看到孩子自己说的话

之前同步下来的故事书只有角色台词，孩子说的每句都丢了。原因是板子侧挑 `user` 行时
按 2048 字节读，而会话里孩子那一行前面带着整段人设提示词，常常超过 2 KB，
读不全就被当成半行丢掉。v2.93 把行缓冲按提示词上限给足，并只摘 `[USER]` 后面那句。

| # | 做什么 | 该看到什么 | 结果 |
| --- | --- | --- | --- |
| 18.1 | 进故事模式，**孩子说 3 句以上**（长一点更好），再说「把这次冒险放进故事书」 | 串口 `share: 已复制 N 条到 kid_buddy:share` | |
| 18.2 | 家长端点「同步故事书」 | 打开故事书，**蓝色的「孩子：」行和角色台词交替出现**，不是只有灰字正文；正文一句一行，孩子的话和故事是同一套字体、同一个字号 | |
| 18.3 | 逐句对照板子上的字幕板 / 串口 | 孩子那几行的文字与当时说的一致，**没有混进**「[SYSTEM]」「[USER]」或人设文字 | |
| 18.4 | 同步完成后看串口 | 没有 `publish failed` / `Reconnecting`；手机从「收到 N/M 片」走到「本机共 N 条」 | |

**注意**

- 家长端按 `(role, ts, content)` 去重，**旧版本同步过的记录不会被改写**。
  验这一条之前先在设置里点「清空记录」再同步，否则看到的是旧数据。
- 孩子那句话本身特别长时，家长端显示会被截断，那是手机侧存档的长度限制，
  不是这次的问题。

### 18B. 家长端四个「设定」按钮不能把 MQTT 卡死

之前点「留言 / 睡觉时间 / 名单 / 起名字」之后，家长页停在「同步中」，板子也再不
回消息，只能重启。根因是回执在 MQTT-C 的 `on_publish()` 回调里直接发，
而回调持有非递归的 client 锁 —— 发一条就自己等自己。v2.93 改成排进队列，
等 `mqtt_sync()` 返回、锁放开后由 sync 线程发。

| # | 做什么 | 该看到什么 | 结果 |
| --- | --- | --- | --- |
| 18.5 | 依次点「留言」「睡觉时间」「名单」「起名字」各一次 | 每次都有回执；串口**不出现** `mqtt_sync error` / `Reconnecting` | |
| 18.6 | 四个按钮点完，马上再发一条普通留言 | 板子照常念出来 —— 通道还活着 | |
| 18.7 | 点「同步故事书」 | 照常回传，不停在「同步中」 | |
| 18.8 | 连续快速点同一个按钮 6 次以上 | 串口可能出现 `ack 队列满`（队列 4 条），但之后仍能正常收发 | |
| 18.9 | 重启板子，重复 18.5 | 同样正常 —— 这个修复不依赖运行状态 | |

**注意**

- 判断「卡死」看的是**之后还能不能收发**，不是某一条回执有没有来。
  单条回执丢了（队列满）不影响通道。
- 如果仍然卡住，串口里应该能看到 `mqtt_sync error:` 或 `Reconnecting`；
  把这两行发我，说明还有第二条路径在回调里发送。

## 记录格式建议

出问题的时候，把这三样一起发我，基本就够了：

1. **哪一项**（编号，比如 2.5）
2. **串口日志原文**（从最后一个正常行开始，往后贴十几行）
3. **屏幕上的现象**（脸是什么表情、字幕板写着什么）

有条件的话加一条：**这条能不能稳定复现**（每次重启都这样，还是只出现了一次）。
